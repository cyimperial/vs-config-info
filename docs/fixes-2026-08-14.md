### B4 — unguarded, expensive razor builds

`New-RazorMatrix.ps1` replaces the inline `md razor` / `--force` sequence:

| Risk | Mitigation |
| --- | --- |
| Ran immediately, no confirmation | **Dry run by default**; `-Force` required to build |
| All TFMs shared one folder, `--force` overwrote each other | Each TFM builds in its **own** subfolder |
| Could overwrite user files | Refuses a non-empty work root without its own `.vs-config-info` marker |
| Failed hard when a TFM's SDK was absent | Unsupported frameworks are **skipped** and reported |
| Left hundreds of MB behind | `-Cleanup` switch |
| All-in-one triggered it silently | `SKILL.md` requires an `ask_user` confirmation first |

The old instructions would have failed outright on net9.0 and net8.0.

# Hardening round 2 — P1 / P2

A follow-up review asked what still needed improving. Two items were actioned.

## P1 — StrictMode-safe property access

Under `Set-StrictMode -Version Latest`, reading a property a JSON object does not carry throws
`PropertyNotFoundStrict` (verified, not assumed). `vswhere` output varies by install: a minimal
instance has no `catalog` node at all, so `$vs.catalog.productDisplayVersion` could take down
the whole collector in a caller's strict-mode session.

```powershell
# Before - throws under StrictMode when the node is absent
$display = $vs.catalog.productDisplayVersion

# After
$display = Get-JsonProperty $vs 'catalog.productDisplayVersion'
```

`Get-JsonProperty` walks a dotted path via `$obj.PSObject.Properties[$name]`, which returns
`$null` safely, and accepts a `-Default`. Every optional vswhere/registry read now goes through
it.

While auditing for this, four helpers (`ConvertTo-SortableVersion`, `ConvertTo-SafeFileNamePart`,
`Format-JsonIndent`, and the new `Get-JsonProperty`) were found duplicated across scripts and
were consolidated into `VsConfigInfo.Common.ps1`. A static test now asserts each helper is
defined exactly once.

## P2 — Test suite and CI

`tests/Invoke-SkillTests.ps1` — 30 tests, no Pester dependency, `%TEMP%`-isolated. Every
blocker above now has a named regression test. `.github/workflows/test.yml` runs it on
`windows-latest`. Full details in [`testing.md`](testing.md).

## Bug the tests immediately caught

The .NET SDK was uninstalled from this machine by an unrelated actor midway through the work,
which put the collector on a code path nobody had exercised: **a machine with a host runtime but
no SDK**.

`dotnet --info` on such a machine starts at `Host:`, and the old pattern matched the first
`Version:` line anywhere in the output:

```powershell
# Before - on a machine with no SDK this returned the *host* version (8.0.30) as SdkVersion
if ($info -match '(?m)^\s*Version:\s*(.+)$') { $sdkVersion = $Matches[1].Trim() }

# After - only ever reads the ".NET SDK:" block
if ($info -match '(?ms)^\.NET SDK:\s*\r?\n(.*?)(?:\r?\n\s*\r?\n|\z)') { ... }
```

The skill's own design rule is *never fabricate configuration values*; reporting a host runtime
as an installed SDK broke it. Fixed, plus `SdkCount` and `InstalledSdks` were added so the
answer is explicit rather than inferred, and a regression test asserts `SdkVersion` is `$null`
whenever `SdkCount` is `0`.

`New-RazorMatrix.ps1` had a related flaw: a **dry run** threw when no framework was buildable.
A dry run is a question, and "nothing to build" is a valid answer — it now returns a plan and
only throws under `-Force`.

# P4 — host compatibility

`Add-Type -AssemblyName System.Drawing` sat bare at the top of `VsConfigInfo.Common.ps1`, and
there was not a single version or platform check anywhere in `scripts/`. On PowerShell 7 that
line fails, because GDI+ moved out of the shared framework into the `System.Drawing.Common`
package — so every format would die with `Cannot add type` and no hint about what to do. The
README meanwhile advertised "5.1 or later".

Dot-sourcing `Common` now calls `Initialize-VsConfigDrawing`, which resolves the host first:

| Host | Assembly | Result |
| --- | --- | --- |
| Windows PowerShell 5.1 | `System.Drawing` (GAC) | Loads — the verified host |
| PowerShell 7 on Windows | `System.Drawing.Common` | Loads if the package is present, otherwise throws a message naming both remedies |
| Any non-Windows host | — | Refused up front; the skill also needs `cmd`, `vswhere` and the registry |

```
PowerShell 7.4.6 cannot load GDI+: the assembly 'System.Drawing.Common' is not available,
and PowerShell 7 does not ship it.
Either run this skill under Windows PowerShell 5.1:
    powershell -NoProfile -ExecutionPolicy Bypass -File <script>.ps1
or install the package first:
    Install-Package System.Drawing.Common -Scope CurrentUser
Underlying error: Cannot add type. The assembly 'System.Drawing.Common' could not be found.
```

Platform detection uses `[System.Environment]::OSVersion.Platform`, not `$IsWindows`, because
`$IsWindows` does not exist on 5.1 and referencing it under `Set-StrictMode` throws.

## Testing a host that is not available

The interesting branches are exactly the ones a 5.1 box can never execute. Instead of marking
them untestable, the decision was split from the effect: `Get-VsConfigDrawingPlan` is pure and
accepts `-Edition` / `-OnWindows`, and `Initialize-VsConfigDrawing` accepts an injected `-Plan`.
Seven tests now cover both editions, both platforms, the actionable message and idempotency —
all from 5.1.

`Assert-Throws` gained a `-MessageLike` parameter so a thrown message can be asserted rather
than merely counted, and it now pipes body output to `Out-Null` to stop stray output leaking
into the run log.

# P3 — making the razor build reachable

`New-RazorMatrix.ps1 -Force` was the last completely unexercised path in the skill. It could not
be run here: it requires an installed SDK matching each requested framework, and this machine
has none. Leaving it permanently untested was not acceptable for the one piece of code that
does destructive, expensive work.

GitHub's `windows-latest` image ships several SDKs, so the build now has a home:
[`.github/workflows/razor-matrix.yml`](../.github/workflows/razor-matrix.yml). It is a separate,
`workflow_dispatch`-only workflow — never attached to `push` or `pull_request`, because a
self-contained `win-x64` publish costs roughly 100–200 MB per framework.

It asserts three things the local suite cannot:

| Check | Why the local suite cannot do it |
| --- | --- |
| The dry run creates nothing **when a build is genuinely possible** | Locally nothing is buildable, so the guarantee is vacuous |
| The build emits a PNG and reports runtime packs per framework | Requires a real `razor.deps.json` |
| `-Cleanup` actually removes the scratch folder | Requires a scratch folder to have been created |

The rendered PNG is uploaded as an artifact, because looking at the image is the only way to
confirm a renderer is correct.

## The workflows are now tested too

Adding CI meant writing ~40 lines of inline PowerShell inside YAML — reintroducing exactly the
defect class that produced blocker B1, in a new file type. So the suite now extracts every
`run: |` block belonging to a `shell: powershell` step and parses it:

```
PASS  PowerShell inside the CI workflows parses (B1 regression, new file type)
PASS  the expensive razor build is opt-in only (B4 regression)
```

The extractor is hand-rolled — PowerShell 5.1 has no YAML parser, and taking a module
dependency would defeat the point of a self-contained suite. It was verified by dumping what it
extracted (4 blocks, correct first and last lines) rather than trusting a green result, since a
broken extractor finding zero blocks would also have "passed". The count assertion guards that.

Workflow inputs are passed through `env:` rather than interpolated into the script body, so
nothing typed into the dispatch form is ever parsed as PowerShell.
